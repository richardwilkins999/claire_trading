# Claire Trading — technical-debt, efficiency and UI review (2026-11-11)

Read-only review at commit `61229a2`. No project file, service or database
row was changed. Four parallel reviewers read every file in `app/`, `web/`,
`bin/`, `mcp/` and `systemd/` in full; I ran the tests and linter, walked
every dashboard page at desktop and phone width, timed the endpoints, and
re-checked the findings marked **[V]** against the code or the live
database myself. Unmarked items are a reviewer's reading of the code that I
did not re-check. The 2026-11-03 review covered security; this one does not
repeat it.

**Summary.** The safety design is sound and the 2026-11-03 fixes held, but
the code has grown by re-implementing things per feature instead of sharing
them, and that duplication has started to produce wrong numbers on screen
and a few real bugs on the money path. Nothing is slow today; the
efficiency problems are wasted LLM turns and oversized polled payloads, not
response times. The UI's biggest gaps are that no page answers "what do I
hold, what protects it, what is pending", totals mix SGD and USD, and paper
versus live is easy to miss.

One thing to know about this review itself: `tests/test_smoke.py` runs
against the live services when they are up, so each of my three full test
runs sent one real "status?" chat turn to Claire and one live quote request.

## 3. Technical debt

### 3.1 The same thing implemented many times

This is the dominant pattern and the source of most bugs in section 2.

| Concept | Copies | Consequence |
|---|---|---|
| Position / holdings / P/L | 11+ places, three rounding rules (integer truncation, float, Decimal) — `repo.py:552`, `repo.py:276`, schema views, `custodian.py:464`, `watcher.py:115`, `portfolio.py:27`, `price_triggers.py:122`, `claire_agent.py:82`, `desk.py:376`, four more in `dashboards.py`/`telegram_approvals.py` | B5 and the average-cost bug |
| Price → account currency | 6 in the core modules plus 5 in the HTTP layer, each with a different failure policy | B3 |
| Saxo HTTP access | 5 request wrappers, 4 error conventions, 3 throttles (none handles 429), 4 instrument resolvers, 2 order builders — `saxo_live.py`, `saxo_broker.py`, `saxo_chart.py`, `mcp/saxo_mcp.py` | Token refresh is the one thing done once |
| Exchange facts (suffix, currency, lot, vendor code) | 11 tables in 7 Python files, plus the ten-exchange table hard-coded in 5 web pages; "100 if SGX else 1" in 9 places | B10, B12 |
| "POST to claire-api and translate the error" | 8 copies with different timeouts, JSON handling and secret header | B1 |
| "What started this run" | 3 classifiers parsing free text, already disagreeing (web, Telegram, Usage) | Same run labelled three ways |
| Order validation rules in the browser | about 12 copies; the Saxo 25% limit is a literal in 8 | Two order editors and two trigger editors that behave differently |
| Number, money and time formatting in the browser | 6 price formatters with 3 rounding rules, 4 `money()`, 6 timestamp formats | 5.123 shows as "5.12", "5.123" and "5.12 SGD" on different pages; B13 |
| Account label | 5 names for one account ("saxo-paper", "Saxo SIM (paper)", "Saxo SIM 22922395 — paper", "saxo", "Saxo SIM — paper") | |
| Order / work-item states | String literals at 50+ sites; the "open order" tuple re-typed in SQL 22 times in 4 variants, while `order_control.WORKING` and `repo.TERMINAL_ORDER` exist unused | `cancelled` and `resuming` are used but not in the schema comment |

**What to build once:** `positions`/valuation in `repo`; `market.price_in(symbol, ccy)` returning price, rate and age; one `SaxoClient`; one exchange registry served to the browser through `/api/exchanges`; one `ClaireApi` client; a structured `origin` column on work items; `states.py`; and one shared formatter and one order validator in the web layer with limits supplied by the API.

### 3.2 `dashboards.py` is a 3,547-line module

- `create_server` is a 2,775-line closure holding the `Handler` class and about 60 view methods, so no view can be imported or tested without a live HTTP server.
- Routing is a 56-branch `if u.path ==` chain with about 300 lines of business logic inline in `do_POST`, and the error-handling tail pasted three times.
- 13 of 26 POST routes re-check the key ad hoc; `/api/account-action`, which moves ledger cash, uses a weaker variant.
- Domain modules import its private names (`watchlist.py` imports `_levels`, `_approval_account`, `quote_units`), and it reaches into `graph.nodes_execution`, pulling LangGraph into the dashboard process.
- `_trade_check` builds a full set of broker adapters, including a new Saxo client that is never closed, on every request.

Suggested split, lowest risk first, keeping `app/dashboards.py` as a thin
facade because tests import from it:

1. `app/dash/usage.py` — already pure, no closure state.
2. `app/levels.py`, `app/accounts.py` — the helpers other modules already import.
3. `app/dash/claire_api.py` — the one client (fixes B1 on the way).
4. Route table and one error wrapper, done in place before anything moves.
5. A `Ctx` dataclass replacing closure capture.
6. Read-only views by area (`views_system`, `views_runs`, `views_orders`, `views_approvals`, `saxo_pages`).
7. `actions.py` — the POST handlers, last, one route per commit.

### 3.3 "repo is the only writer" is no longer true

`repo.py:1-2` states it; `orders` is updated by raw SQL in `protection.py`,
`custodian.py`, `nodes_execution.py` and `order_control.py`, and
`work_items`/`events` are written from 9 modules. Only four code paths use
a transaction; `set_state`, `thesis_action` (token → event → thesis as
three commits) and `order_control.edit` are sequences of autocommits, so a
crash mid-sequence leaves a half-applied transition. Fix: `repo.cancel_order`,
`repo.add_event`, and a `with repo.tx():` helper.

### 3.4 The schema lives in five places

`schema.sql`, `db.MIGRATIONS` (33 statements re-run on every start, "already
applied" detected by the substring "duplicate column"), and ad hoc
`CREATE TABLE` in `telegram_approvals.py`, `arbiter_notes.py` and
`tools/brokers.py`. Nine columns, three indexes — including the unique
indexes that enforce two of the 2026-11-03 fixes — and one table exist only
through migrations. There is no schema version. Fix: `PRAGMA user_version`
with numbered migrations and a squashed `schema.sql`; this also fixes
`claire-reset` missing tables.

### 3.5 Errors disappear

- The app has no logging: one use of `logging` in the whole of `app/`, and it is a filter. `var/log/api.log` has 64,445 lines, no timestamps, no tracebacks, and 113 HTTP 500s with no stack.
- 153 broad `except Exception` handlers across the app, 33 of them bare `pass`/`continue`; 49 sites truncate the error text to 80–500 characters.
- Consequences already seen: B1, B4 (a dead search looks like "no results"), and a TradingView outage is indistinguishable from "0 hits" in the hourly scan.
- The scheduler wraps its whole tick in `except Exception: pass` (`scheduler.py:280-283`) and runs every job inline, so the screener's LLM call or a backup blocks the 2-minute trigger tick and the 5-minute custodian.

Fix: `logging.basicConfig` with timestamps, `log.exception` in every
swallowing handler, and a per-source failure counter the maintainer reads.

### 3.6 Configuration, deployment and docs

- **Config:** 42 environment variables read at 45 sites in 19 files; the example file documents 20 of them; three boolean conventions (`IBKR_ENABLED=0` enables it); three parsers of the same env file with different quoting rules.
- **Deployment:** four of the five systemd units point at `/opt/Claire`, which does not exist. The one installed unit is a one-shot, so a crashed claire-api is never restarted.
- **Dependencies:** 27 of 86 installed packages are pinned; `langchain-openai` is missing, so four seeded providers cannot work.
- **Docs:** README's test count, "MCP configs activate when credentials exist", the Yahoo-first description and the systemd snippet are all stale; `DESIGN.md` still describes `/opt/Claire` and says no custodian or reconcile is scheduled.
- **Thread safety:** one `SaxoBroker` is shared by the scheduler, run threads and API workers with no lock around its throttle; the paper sim's order dict is iterated while another thread can insert. Not observed failing.
- **Floats in the ledger modules:** `check_risk` sums and compares in float; `order_control.py:140` rescales a cash reserve in float; trailing peaks and thresholds are stored REAL. `record_fill` itself is clean.

### 3.7 Tests

- 30 seconds of the 95 are spent in fixture teardown: each test server uses `serve_forever()` with its default 0.5 s poll, across about 60 tests [V]. Passing `poll_interval=0.01` fixes it.
- Another 17 s is `test_control_script` signal-drain cases and 13 s is the live chat call in `test_smoke.py`.
- `test_smoke.py` should be opt-in (a marker or env flag) so the default suite never touches the running desk.
- Fixtures are shared by importing from other test files (16 cross-test imports) instead of `conftest.py`; one test in `test_control_script.py` checks "in flight" by regex over the shell script's text because the logic is Python embedded in a bash heredoc (`bin/claire:62-176`).

## 4. Efficiency

Nothing is slow for the user today, and `desk.db` is small (129 work items,
149 orders). The waste is in LLM turns, network calls and polled payloads.

### 4.1 LLM and data spend — the real cost

1. **Fix search (B4).** About three wasted turns per news run and eight dead searches per scan, and the agents' evidence gets real.
2. **Give each SDK conversation a wall-clock timeout and cap concurrency.** Each LLM call spawns a `claude` subprocess, 10 per pipeline run; nothing bounds a hung one, and N concurrent runs means 3N processes (`claude_sdk.py:262-442`).
3. **Use a real multi-turn session for chat (B8)** instead of re-sending the flattened history, which also loses cache continuity between turns.
4. **Merge each analyst's tool loop and structured extraction** into one session: 3 fewer subprocess spawns of 10 per run.
5. **`fetch_page` returns the first 6,000 characters of tag-stripped HTML**, mostly navigation [V in a transcript]. Extract the main content first.
6. **Twelve Data budget counts calls, not credits.** One `spark()` call for N symbols spends N credits but 1 budget unit; a 429 discards the partial results. claire-api and the dashboards each run their own budget of 7/min against a quota of 8/min, with separate caches.
7. **The custodian makes one Saxo call per working order** every 5 minutes (12 today, growing by 2 per position). List working orders first and fetch detail only for those that changed.
8. **Quotes are fetched one symbol per call** in the watcher and sim-trigger check, and the cache is keyed by the exact symbol tuple, so singles and batches never share.

Prompt caching is working on the tool loops (about half of input tokens are
cache reads). A cross-agent tool-result cache is not worth building: only 11
of 219 fetched URLs were duplicated across agents in a run.

### 4.2 Dashboard payloads and polling

| Page | What it polls | Cost |
|---|---|---|
| Trading | `/api/runs` (110 KB) then `/api/feed` (70 KB), every 8 s | about 1.35 MB/min per open tab; about 350 queries per poll for 50 runs that are all finished |
| Approvals | `/api/approvals` (121 KB) every 30 s and on each live event | 99% of it is the full reports of 12 already-decided runs inside a collapsed section, with nothing pending |
| Mission Control | 4 endpoints every 20 s | whole SVG map rebuilt each time |
| Agents | 3 endpoints every 15 s | wipes unsaved edits |

Fixes, in order of payoff:

1. Drop `thesis_json` from the runs list and `reports` from decided approvals; load them on expand (`/api/run-detail` exists). Cache each finished run's story by `(id, updated_at)`.
2. Fix the feed (B7).
3. Pause polling when the tab is hidden — only the Saxo page does today.
4. Skip the re-render when the payload has not changed; only `trading.html:324` does today.
5. Server basics: the handler speaks HTTP/1.0, so every request is a new TCP connection, thread and SQLite connection; there is no gzip, and pages and static files are re-read from disk with no cache headers [V]. `protocol_version = "HTTP/1.1"`, gzip above 1 KB and an mtime-keyed ETag.

### 4.3 Database

- **Missing indexes** (all full scans on the live DB): `agent_runs(agent_id, started_at)`, `agent_runs(work_item_id)`, `service_health(service, checked_at)`, `orders(status)`, `orders(work_item_id)`, `orders(account_id, instrument_id)`, `work_items(state)`, `executions(account_id, instrument_id, executed_at)`, `lot_closures(lot_id)`. `agent_runs` is scanned every 2 seconds by the live-event poller. Harmless at today's size; one block of `CREATE INDEX IF NOT EXISTS`.
- **N+1 queries** on the auto-refreshing pages: Portfolio about 50 queries for 6 positions; Trades 5–8 per execution with no limit; `/api/agents` 10 scans.
- **Writes on read paths:** `watchlist.view` runs a data migration on every GET; `live_trading.status()` runs two `INSERT OR IGNORE`.
- **Custodian health:** a full JSON report row every tick (2,038 nearly identical "ok" rows in 7 days). One heartbeat row plus a row on change.

## 6. UI — what to change

What works: the plain-language copy on Orders, Trades and Maintenance, the
"what protects it" tiles on Portfolio, and the run stories on Trading are
good. The suggestions below are ranked by how much they change day-to-day
use.

### 6.1 Highest value

1. **Make the home page answer the daily question.** Mission Control today is a service-health strip and an architecture diagram; it shows no holdings, P/L, orders or live state [V]. Put on top: value and P/L per currency, each position with its protection state (at broker / simulated / plan only), unfilled orders, active triggers and pending approvals, each linking through. Move the system map to a "System" tab.
2. **A mode bar on every page.** A persistent "PAPER" or red "LIVE ARMED" strip in the shared nav, and a count badge on Approvals. Today paper versus live appears only on Orders (a ghost button) and on Approvals when armed; Watchlist does not mark the live account in its dropdown and Saxo opens on the LIVE tab by default.
3. **Fix the money display (B5).** Per-currency subtotals or one stated base currency; a currency on every amount; one formatter. "PAPER CASH 255,791" and "EQUITY 327,003.45" are currently sums of USD and SGD with no label [V].
4. **One trade ticket.** Buying from Watchlist takes five clicks, two native dialogs and two pages, filling in the same order panel twice (Buy now → Send to approval → confirm → Approvals → Approve → confirm). "Buy now" and "Sell now" do neither. Open the approval card's own panel in place and rename the buttons "Buy…" and "Sell…".
5. **Replace native dialogs on money actions.** There are 19 `confirm()`, 4 `prompt()` and 5 `alert()` calls, including arming real-money trading and approving a live order by typing "LIVE" into a browser prompt. Use an in-page confirmation showing side, shares, price, both currencies, account and a LIVE badge.
6. **Reject needs a guard.** It is one click, with no confirmation and no undo, directly beside Approve [V].
7. **Make protection editable where it is shown.** The stop-loss and take-profit rows on Orders and the tiles on Portfolio have no actions; the help text sends you to Saxo's own platform. "Plan only — no order, nothing sells here" is a key risk state shown as small footer text [V] — make it a warning badge.

### 6.2 Navigation and layout

8. **Group the menu.** Thirteen links wrap onto two lines at 1366 px [V]. Three groups — Trade (Approvals, Orders, Portfolio, Watchlist, Markets), Review (Trades, Runs, Usage), System (Agents, Providers, Maintenance, Saxo, map) — with Claire chat as a persistent button.
9. **Phone layout.** No page has a viewport tag, so a phone renders the desktop page at 980 px and zooms out [V]; only `usage.html` has a doctype, so the other 13 pages render in quirks mode [V]. Wide tables (Trades, Watchlist, Saxo, Usage) have no scroll wrapper. Since approvals already arrive by Telegram, Approvals and Portfolio are the two pages worth making work on a phone first.
10. **Deep links that work.** Five pages link to `/trading#<run>` and four to `/approvals#c-<id>`; neither page reads the hash, and Trading only holds the latest 50 runs.
11. **Trading page.** The nav says "Trading", the heading says "Runs". Replace the free-text ticker and manual exchange with the symbol search Markets and Watchlist already have, add status filters, and fix the feed (B7).
12. **Links are browser-default blue on the dark background** [V] — there is no base `a` style outside the nav. Add one, plus `color-scheme: dark` so native selects and scrollbars match.

### 6.3 Clarity

13. **One vocabulary.** The same things are called run / pipeline / work item / thesis / verdict / decision; stop / stop-loss / "give up" / "thesis stop"; trailing alert / trailing floor / price alert (against trailing stop and price trigger, which are different things). Pick one of each, and hide raw `wi_…` ids and rule codes such as `trail_pct` behind "details".
14. **Times.** Every timestamp is browser-local with no zone label; Watchlist prints raw ISO strings; expiries are absolute times with no countdown. Show "in 2 h 10 m (16:00 SGT)".
15. **Stale and error states.** Six pages silently stop refreshing while any input has focus, and Approvals still says "live". Most pages have no error state: a failed fetch leaves a blank page or stale numbers. One shared poll wrapper driving a header pill ("updated 12:03" / "paused while editing" / "cannot reach Claire").
16. **Don't wipe edits.** Agents rebuilds every 15 s and discards an unsaved model change; Orders closes its expanded sections every 30 s.
17. **Jargon on the approval card.** "conviction 0.62", "PASS", "arbiter", "ATR 14", "SMA 20", a raw `sell_review` pill. Evidence sources are plain text, not links.
18. **Accessibility baseline.** No `aria` attributes, no `label for`, clickable rows that are not keyboard-reachable, no focus styles, muted text at 3.8–4.2:1 contrast used for 9–11 px text, and status dots that rely on red versus green alone.
19. **Claire chat.** History is lost on reload though the server keeps the thread; tool calls show as raw JSON; Enter double-sends while a reply is streaming; the intro says approvals are on Mission Control.

One observation, not a recommendation: with the dashboard bound to
`0.0.0.0`, the read endpoints (`/api/portfolio`, orders, trades) answer
without the dashboard key [V], so holdings and P/L are readable by anyone
on the home network. The real Saxo account page is key-protected. This
looks deliberate (the August "serve the dashboards on the LAN" change).
